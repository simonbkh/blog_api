# Blog API Service (Go + PostgreSQL)

A modular blog service using clean architecture boundaries:

- Domain: entities and repository contracts
- Application: auth/RBAC and post use cases
- Infrastructure: PostgreSQL (GORM) adapters + migrations
- Interfaces: REST API, middleware, and minimal Vue admin UI

## Why GORM

GORM was chosen for this version to accelerate CRUD-heavy delivery while preserving architecture boundaries through repository interfaces. SQL injection risk is reduced by parameterized queries generated by GORM APIs and strict input validation at handler/use-case boundaries.

## Project Structure

- `cmd/api/main.go`: composition root and server lifecycle
- `internal/domain`: core entities and repository interfaces
- `internal/application`: use cases and RBAC/auth services
- `internal/infrastructure/persistence/postgres`: DB connection, repos, migration runner
- `internal/interfaces/http`: router, middleware, handlers, API error/JSON helpers
- `migrations`: SQL schema files
- `web/admin`: minimal Vue SPA served at `/admin/`

## API Endpoints

### Auth

- `POST /auth/login`
- `POST /auth/refresh`
- `POST /auth/logout` (requires access token)
- `GET /me` (requires access token)

### Posts

- `GET /posts`
- `GET /posts/{id}`
- `POST /posts`
- `PUT /posts/{id}`
- `DELETE /posts/{id}`

### System

- `GET /healthz`
- `GET /admin/system/health` (super admin only)

## RBAC Rules

- `writer`: CRUD only own posts
- `admin`: CRUD all posts
- `super_admin`: full access, including system-level admin route

## Security Design

- JWT access tokens with short TTL (`ACCESS_TOKEN_TTL`)
- Opaque refresh tokens with DB-backed rotation and revocation
- Strict JSON decoding (`DisallowUnknownFields` + body size limit)
- Strict CORS allowlist via `ALLOWED_ORIGINS`
- Per-IP and per-user rate limiting middleware (concurrent-safe)
- Sanitized API error messages (no sensitive leaks)

## Database Schema

Migration files:

- `migrations/001_init_users.sql`
- `migrations/002_init_posts.sql`
- `migrations/003_init_refresh_tokens.sql`

## Local Run

1. Start PostgreSQL:

```bash
docker compose up -d postgres
```

2. Configure env:

```bash
cp .env.example .env
```

3. Run API:

```bash
make run
```

4. Open admin UI:

- `http://localhost:8080/admin/`

## Example Requests/Responses

### Login

Request:

```http
POST /auth/login
Content-Type: application/json

{
  "email": "admin@example.com",
  "password": "ChangeMe123!"
}
```

Response:

```json
{
  "tokens": {
    "access_token": "...",
    "refresh_token": "...",
    "expires_at": "2026-03-27T10:10:00Z"
  },
  "user": {
    "id": 1,
    "email": "admin@example.com",
    "role": "super_admin"
  }
}
```

### Create Post

```http
POST /posts
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "title": "First post",
  "content": "Hello from clean architecture.",
  "status": "draft"
}
```

### List Posts

```http
GET /posts
Authorization: Bearer <access_token>
```

Response (writer sees own posts only, admin/super_admin sees all):

```json
[
  {
    "id": 1,
    "title": "First post",
    "content": "Hello from clean architecture.",
    "author_id": 1,
    "status": "draft",
    "created_at": "2026-03-27T09:00:00Z",
    "updated_at": "2026-03-27T09:00:00Z"
  }
]
```

## Notes

- Migrations are auto-run at startup from `migrations/` in lexical order.
- A super admin user is bootstrapped when `SEED_SUPERADMIN_EMAIL` and `SEED_SUPERADMIN_PASSWORD` are provided.
- This service is designed to be extracted as a microservice: domain/app layers remain framework-agnostic.
